# 04 · Findings → Cloudflare Controls

**Engagement:** Harbor & Heath Outdoor Co. — Cloudflare origin-readiness POC
**Audit run:** `harbor-heath-run-1`

This is the operational core of the pack. It maps every validated record to the allowed Cloudflare control set, the policy intent, the residual origin work, the owner (origin / edge / shared), and whether it is a launch blocker.

## Ground rules

- **No invented Cloudflare products.** Only: DNS, TLS Full (strict), proxied records / hide origin, WAF custom rules, managed WAF, rate limiting, Bot Management, Turnstile, API Shield / schema validation, Zero Trust Access (SSO on /admin and operator APIs), Cache Rules, Workers (header normalization, webhook signature verification at edge, origin lock checks), DDoS protection, Logpush / security analytics.
- **No severity on `needs_validation`.** A lead is a launch blocker only when the origin *must* be fixed regardless of validation, because the edge cannot compensate (object-level authz, order-state integrity).
- **Defense-in-depth gaps are hardening notes**, not vulnerabilities (cookie flags, Referrer-Policy).
- **If a control already blocks the issue at a higher layer, a missing lower layer is not a confirmed vuln** — the CSRF rejection is the example.

## Narratives — HIGH-VALUE items

### A. Object-level authorization gap (IDs 1–4)

**What we saw:** the consumer commerce surfaces (cart API, GraphQL order query, Stripe payment-intent mint, PayPal create) authenticate nothing about *object ownership*. Every handler locates the resource by a client-supplied uuid and checks at most status (`status=true`), `payment_status='pending'`. The uuid is `gen_random_uuid` (122-bit) — not guessable — which is why this is `needs_validation` (reachability depends on a leak channel) — but the **authorization control is absent** and no edge can synthesize it.

**Why it matters for checkout/admin/webhooks:** the checkout is where the money path and the PII path intersect. An attacker with a leaked uuid (shared checkout URL, history, logs, admin screenshots, referrer) can read PII, hijack a cart, mint payment intents, and re-point PayPal orders.

**Exact edge control:** Turnstile + rate limiting on `/api/carts`, `/api/orders`, `/api/stripe/paymentIntents`, `/api/paypal/orders`; Bot Management on checkout; API Shield schema validation to force a well-formed, rate-limited contract — to make automated uuid-enumeration and abuse unrewarding.

**Residual origin work:** add an ownership predicate on every consumer object access: bind cart→session/customer, order→customer, paymentIntent→order+customer, PayPal→order+customer; a scoped "my cart" API instead of url-ishing uuid APIs.

### B. Webhook order-state integrity (ID 4 → the state machine)

**What we saw:** the Stripe webhook's `payment_intent.canceled` branch writes `payment_status='canceled'` for any non-canceled state, including `stripe_captured`, with no still-pending requirement, bypassing the `cancelOrder` cancelability gate, and emits no refund/restock/`order_canceled` events — while the hook-after path re-projects `order.status='canceled'`.

**Why it matters:** a settled order silently becoming "canceled" with no refund, no restock, and no notice is a customer-trust and inventory-integrity failure; on a late/redelivered cancellation it can hit a *paid* order.

**Exact edge control:** Workers webhook-verification — re-verify the Stripe signature at the edge and forward only signed, allowlisted event types to the hooks origin path; keep webhooks on their own hostname with origin lock.

**Residual origin work (blocking):** the canceled branch must require `still-pending`, route through the cancelability gate, and emit proper rollbacks/events. This is origin-only — the edge can verify the caller, not the order's row state.

### C. Credential surface & rate limiting (IDs 9–10)

**What we saw:** the JWT-mint endpoints run bcrypt under the permissive `api` tier (120/60s → 300/60s via locale-prefixed path) instead of the `auth` tier (8/15min), and the IP-bucket key is attacker-influenceable via `X-Forwarded-For` when `TRUST_PROXY_HOPS` defaults to 1 and the app is directly exposed (compose).

**Why it matters:** credential-stuffing against operator and shopper accounts at ~2–5 guesses/second/IP is often enough to matter, and it's exactly what Cloudflare is paid to blunt.

**Exact edge control:** strict rate limiting (auth-tier-like budgets) on `/api/user/tokens`, `/api/customer/tokens`, `token/refresh`, plus path-alias coverage via WAF custom rules; **Workers header normalization** to strip/overwrite client `X-Forwarded-For` so edge rate limits use the true client IP; Bot Management on login.

**Residual origin work:** move the mint paths to the auth tier in origin and fix `TRUST_PROXY_HOPS` to match the real proxy depth. Owner (origin ops) must confirm the edge actually overwrites XFF before the compose-direct exposure changes.

### D. Secrets and defaults (IDs 8, 22, and hardening notes)

**What we saw:** `keyboard cat` as the operative cookie secret when no real secret is provisioned; compose publishes a known-credentialed Postgres.

**Why it matters:** a known signing secret is identity forgery; a published DB with known credentials is data theft. Neither requires any "vulnerability" label — they are operational decisions that must be reversed before cutover.

**Exact edge control:** TLS Full (strict), hide the origin (proxied records), and **origin lock** the allowlist to Cloudflare; Access SSO on admin. Edge cannot change the origin's secret.

**Origin work (blocking, cheap):** provision and rotate a real `session.cookieSecret`, bind DB to loopback (remove the 5432 publish), rotate to generated credentials. Both are one-day fixes owned by origin ops.

## Owner legend

- **origin** — change must land in the application or its deployment.
- **edge** — change lands in the Cloudflare control plane (zone, Workers, Access policy).
- **shared** — edge gives day-one mitigation; origin change is required or recommended for the durable fix.
